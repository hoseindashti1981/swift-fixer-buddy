# نگهداری محتوای نسخه ۲

قرارداد اجرایی داده در [content-schema.ts](../src/data/content-schema.ts) است. داده تولیدشده را مستقیم ویرایش نکنید.

## ورودی‌ها

- `src/data/notes.json`: آرشیو اصلی ۱۶۲ یادداشت قدیمی؛ متن آن برای بازبینی حفظ شده و اپ آن را import نمی‌کند.
- `src/data/quarantine.json`: تصمیم‌های صریح توقف انتشار با شناسه و علت.
- `content/articles.json`: مقاله‌های جدید و نسخه‌های اصلاح‌شده با ساختار کامل نسخه ۲؛ تعداد جاری را `content:check` گزارش می‌کند.
- دو مرجع Markdown در `Mr Ahi Class`: متن کلاس از همین فایل‌ها خوانده می‌شود. سه نمونهٔ نخست، خلاصه و شناسهٔ پایدارشان را از `content/articles.json` می‌گیرند.

برای شروع یک پیش‌نویس می‌توان ساختار یک رکورد `content/generated/archive.json` را کپی کرد، شناسه مستقل تعیین کرد و وضعیت را `draft` گذاشت. منشأ، منبع و دامنه باید مطابق شواهد واقعی نوشته شوند. نام فایل آرشیو، منبع تأیید فنی محسوب نمی‌شود. فیلد نامعلوم با null یا آرایه خالی ثبت شود؛ مدل، مقدار فنی و منبع از روی عنوان حدس زده نشوند.

## دستورها

```powershell
bun run content:generate
bun run content:check
bun run typecheck
bun test tests/content-import.test.ts tests/content-safety.test.ts
bun run build
node tests/vercel-output.mjs
```

دستور generate خروجی‌های زیر را تولید می‌کند. دستور check بدون نوشتن، ورودی‌ها را اعتبارسنجی و خروجی‌ها را با نتیجه بازتولید مقایسه می‌کند. build و build:dev ابتدا check را اجرا می‌کنند. خطای ورودی باید پیش از ساخت رفع شود. نسخه تولیدشده فایل‌ها باید همراه ورودی‌های مربوط نگهداری شود.

## ساختار مقاله

شناسه، عنوان، دسته، برچسب و متن قدیمی برای سازگاری با نمایش و جست‌وجوی فعلی حفظ شده‌اند. `content` شامل این بخش‌هاست:

| بخش | کاربرد |
|---|---|
| schemaVersion / revision / kind | نسخه ساختار، ویرایش مقاله و نوع محتوا |
| aliases / symptoms / componentIds / errorCodes / domains | داده مستقل جست‌وجو و طبقه‌بندی |
| scope | نامعلوم، عمومی یا مدل‌های مشخص؛ برند و مدل جدا هستند |
| summary / sections | پاسخ کوتاه و بخش‌های دارای شناسه و پیوند منبع |
| possibleCauses / nextSteps | علت با شاهد پشتیبان و اقدام بعدی |
| procedure | پیش‌شرط، ابزار، مراحل، نتیجه مورد انتظار و شناسه منابع |
| measurements | مقدار یا بازه، واحد، شرایط و منبع |
| safety | وضعیت بررسی، خطر، صلاحیت و شرایط توقف |
| sources | منشأ آرشیوی، سند سازنده، مرجع فنی یا مشاهده میدانی |
| publication | وضعیت، امکان نمایش، علت توقف، تاریخ و نام بازبین، رابطه نسخه‌ها |
| observation / relatedIds | مشاهده و نتیجه تجربه، و مطالب مرتبط |

برای هر منبع عنوان، ناشر، URL یا مسیر، شماره و ویرایش سند، محل دقیق در سند و تاریخ دسترسی قابل ثبت است. منبع آرشیوی با شناسه رکورد قدیمی پیگیری می‌شود. این locator با شماره صفحه سند سازنده یکسان نیست.

شناسه بخش از عنوان و شماره تکرار آن ساخته می‌شود؛ افزودن بخش نامرتبط شناسه بقیه را تغییر نمی‌دهد. تغییر عنوان یا جابه‌جایی بخش‌های هم‌نام می‌تواند شناسه همان بخش را تغییر دهد؛ برای مقاله تألیف‌شده شناسه را دستی و پایدار حفظ کنید.

## قواعد انتشار

همه رکوردهای قدیمی با وضعیت needs-review، دامنه unknown و ایمنی unknown تبدیل می‌شوند. عنوان تعمیرگاهی، شماره برند در عنوان و متن reference به‌تنهایی شواهد تطبیق مدل نیستند.

ورودی authored با همان شناسه، نسخه ساختاری مقاله قدیمی را جایگزین می‌کند؛ آرشیو اصلی در notes.json باقی می‌ماند. شناسه جدید مقاله مستقلی می‌سازد. رابطه supersedes/replacedBy را صریح تعیین کنید. شناسه یا ارجاع تکراری و رابطه به مقاله ناموجود رد می‌شود.

وضعیت verified به نام و تاریخ بازبین، خلاصه، دامنه معلوم، ایمنی بررسی‌شده و منابع غیرآرشیوی برای بخش‌ها، علت‌ها، اندازه‌گیری‌ها و روش آزمون نیاز دارد. برای کد خطا، کد صریح، دامنه مدل و منبع سازنده لازم است؛ برای تست، روش کامل؛ برای تجربه، مشاهده و نتیجه. منبع سازنده باید شماره سند و ویرایش داشته باشد. اعتبارسنج وجود و سازگاری این داده‌ها را بررسی می‌کند؛ صحت فنی ادعاها را باید بازبین احراز کند.

draft، superseded و quarantined وارد بسته انتشار نمی‌شوند. needs-review طبق تصمیم فاز ۱ با برچسب قابل مطالعه است. رفع قرنطینه علاوه بر اصلاح مقاله به تغییر صریح تصمیم در quarantine.json نیاز دارد؛ تغییر مقاله به‌تنهایی آن را منتشر نمی‌کند.

## خروجی‌ها

- `content/generated/archive.json`: نسخه ساختاری همه مقاله‌ها، مخصوص کار تحریریه.
- `content/generated/import-report.json`: وضعیت ورود و کمبودهای هر مقاله.
- `content/generated/ahi-class-coverage.json`: نام فایل، بازهٔ خطوط و مسیر مقصد هر بخش کلاس، از پرونده‌های اصلی تا روش‌های تشخیص و نمایه‌ها.
- `src/data/catalogue.generated.json`: فقط مقاله‌های قابل نمایش؛ ورودی واقعی اپ.
- `src/data/legacy-map.generated.json`: نگاشت شناسه‌های قدیمی بدون متن مقاله؛ برای حفظ لینک و تشخیص ویرایش محلی.

آرشیو تحریریه و ابزار تبدیل نباید از کد مرورگر import شوند. فایل‌های content به public کپی نشوند. متن سازگار قدیمی فعلاً همراه بخش‌های استخراج‌شده در مقاله نگهداری می‌شود؛ استفاده از بخش‌ها در Search v2 و رابط جدید در فازهای ۴ و ۵ انجام می‌شود.

داده‌های شخصی با migration نسخه ۲، پشتیبان و بازیابی فاز ۶ نگهداری می‌شوند. در زمان نمایش، متادیتای انتشار ذخیره‌شده کنار گذاشته می‌شود تا ویرایش شخصی ادعای تأیید مرجع را به ارث نبرد.

## چرخه ورود و بازبینی مستمر — فاز ۹

۱. فایل اصلی در `New Subjects` حفظ شود. `extractSubjects` در `scripts/lib/review-subjects.ts` شناسه، محل و SHA-256 متن هر پرسش و پاسخ را استخراج می‌کند. تغییر متن اولیه باید به بازبینی ردیف متناظر منجر شود؛ هش را بدون بررسی صرفاً به‌روز نکنید.

۲. برای هر پرسش یک ردیف در `content/new-subjects-review.json` لازم است. موارد در انتظار شاهد باید تاریخ بررسی، URL منابع بررسی‌شده، دلیل توقف و `neededEvidence` مشخص داشته باشند. `checkedSources` به معنی پشتیبانی کامل منبع از ادعا نیست.

۳. انتشار فقط با بازنویسی مستند در `articles.json` انجام شود. هر بخش باید منبع اصلی، دامنه روشن و شروط ایمنی داشته باشد. ادغام چند پرسش در یک کارت به معنی تأیید تمام متن اولیه نیست. منشأ این کارت‌ها `source-summary` است؛ تجربه میدانی تأییدشده معرفی نشوند. تعریف `verified` در این مجموعه تطبیق متنی توسط بازبین ثبت‌شده است؛ صحت میدانی را تضمین نمی‌کند.

۴. ردیف منتشرشده به مقاله قابل‌انتشار و منبع آرشیوی همان پرسش با مسیر و locator دقیق وصل شود. اعتبارسنج پیش از تولید خروجی، ردیف گمشده، تکراری، هش قدیمی، انتظار بدون دلیل و مقصد نامعتبر را رد می‌کند. مدل و اعداد فنی فقط از سند همان مدل استخراج شوند؛ دامنه عمومی مجوز تعمیم روش اختصاصی نیست.

۵. پس از `content:generate`، `content:check`، تست‌های `new-subjects` و `content`، `guides:check`، `search:evaluate`، `typecheck`، build و آزمون‌های مرورگر آفلاین اجرا شوند. تغییر معنای مسیر عیب‌یابی نیازمند افزایش `GUIDE_REVISION` و شروع دوباره پاسخ‌های قدیمی است. نتایج و موارد باز در گزارش هر نوبت ثبت شوند؛ رفع قرنطینه به شاهد و تصمیم صریح مستقل نیاز دارد.
